# Agent guidelines — gatekeeper extension

This directory is a [Pi](https://github.com/earendil-works/pi) extension that owns Pi's whole permission story: turn plans, permission modes, an AST allowlist + PATH-aware bin trust + LLM auditor for Bash, and — since the sandbox inversion — OS confinement itself. Pi runs unsandboxed; every unprivileged bash command is wrapped in `nono run --profile pi-tools` via the bash tool's `spawnHook` (`src/sandbox/wrap.ts`), user-typed `!` bash is wrapped through the `user_bash` event because it never reaches the tool layer, the in-process file tools are gated by `nono why --profile` queries (`src/sandbox/nono.ts`), and `elevated_bash` escapes everything behind a per-command human dialog. `index.ts` is wiring only; the decision pipeline is `src/gate.ts`.

## Verify

- NEVER: grant the `pi-tools` nono profile (or anything else sandboxed bash can reach) access to an escape channel or privileged resource — the pre-inversion design died exactly this way, when the profile's zmx-socket allowance let unprivileged bash drive the elevation daemon; instead keep all elevation inside the unsandboxed Pi process, behind the per-command approval dialog. No permission mode may weaken this: `sandboxSpawnHook` is installed at Bash-registration time and must never consult `config.mode`, so even `danger` runs Bash inside `nono`. Nor does that hook reach every shell — it is an option on the bash *tool*, so it sees only calls the model made, and a user-typed `!` went through `AgentSession.executeBash` fully unconfined (real `GH_TOKEN`, ambient login PATH, writes anywhere) until 2026-07-30; it is wrapped now by `sandboxBashOperations(...)` from the `user_bash` handler in `index.ts`, and any new Pi entry point that spawns a shell needs the same audit, proven by *running* the wrapper with a sentinel value in `GH_TOKEN` and seeing the child report nono's placeholder instead — never by reading the wrapper. `!!` stays unconfined on purpose — it is the escape hatch that makes confining `!` acceptable, so widen the `pi-tools` profile instead of touching it — and because it doubles as pi's "exclude from context" prefix, the unconfined command is also the one the model never sees; say so wherever `!` is documented. The corollary is that `edit`/`write` have *no* OS sandbox behind them — they are in-process `fs` calls, which is why `manual` mode asks about each one and blocks rather than writing when no human is reachable.
- ALWAYS: prove profile changes from the chezmoi source before any apply — `nono profile validate <source .jsonc>` plus decision probes like `nono why --json --profile <source .jsonc> --allow <cwd> --path <p> --op <op>`; both accept file paths, so no deploy is needed (and the installed binary is the authority — nono's docs undersell its CLI).
- ALWAYS: run `mise run ci` from this directory before claiming a change works — it chains `mise run test` (unit tests, `node:test` via `tsx`; needs the `nono` CLI on PATH or the gate probes soft-skip) and `mise run bundle` (the esbuild check, the only type-adjacent check available because Pi's packages resolve only inside Pi). Either runs alone. Run `mise run deps` (`aube ci`) after any manifest edit. The aggregate is deliberately not called `check`: the repo root defines `check = "hk check"`, and a same-named task here would shadow that lint lane for every command run from this directory.
- ALWAYS: prove an auditor change against a live model before believing it, because the suite cannot reach `complete()` and a rejected request fails *closed* — `temperature: 0` looked harmless and blocked every audited command until a real run surfaced `Unsupported parameter: temperature` on 2026-07-30. Run `GATEKEEPER_AUDIT_USAGE=1 "$(mise which pi)" -p --gatekeeper-mode auto --gatekeeper-ask never "<prompt that runs several separate bash calls>"` from a throwaway directory and read the per-call `input`/`cacheRead`/`cost` line; that line is the only account of auditor spend anywhere, since these calls bypass `sessionManager` and so appear in neither the session log nor pi's usage display.
- ALWAYS: for behavior tests cannot exercise (dialogs, status UI, mode switching, extension loading), ask Max to drive a TUI session through `~/bin/pi` rather than `"$(mise which pi)"` — the wrapper is what supplies a real session's environment (`fnox`-injected `DATALAB_API_KEY`, `GH_TOKEN`, `PI_OFFLINE`, `SESSION_PLANNER_PLANNOTATOR_BIN`) and warms nono's proxy CA before the TUI owns the terminal, so a bare-binary session tests a configuration nobody runs.

## Module boundaries

- NEVER: put logic worth testing in a module that value-imports `@earendil-works/*` or `typebox` — those resolve only inside Pi, so a single such import makes the whole module unreachable from the suite. Instead split the pure half out and let the Pi-coupled half import it, as `src/tools/claude-args.ts` ↔ `src/tools/builtins.ts` and `src/ui/summary.ts` ↔ `src/ui/dialog.ts` do. `import type` is erased and safe. Tool-name constants the gate reasons about live in `src/policy.ts` for the same reason.
- NEVER: register a Pi built-in tool name (`bash`, `read`, `write`, `edit`, …) from any other extension; instead add it to `src/tools/builtins.ts` here. Registering a built-in name overrides it and the last registration wins, so a second extension claiming `bash` would decide by directory sort order whether the nono spawn hook — i.e. all OS confinement — survives.
- ALWAYS: keep gatekeeper ignorant of other extensions' features; instead take what it needs over `pi.events`. The session-planner extension publishes approved-plan text on `session-planner:approved-plan` and gatekeeper only relays it to the auditor, so deleting that extension leaves nothing to clean up here.
- NEVER: change `src/hazmat/` logic while moving it — those rules are dated and attack-derived, and `test/hazmat/analyze.test.ts` is the proof they still hold. Treat a failure there as a live hole rather than a stale expectation.

## Bash trust

- NEVER: let a command name stand in for the file it runs; instead put every allowlisted name through `checkExecutable` (`src/hazmat/bin-trust.ts`), which resolves it the way bash will (directory part against `cwd`, bare name down `PATH`, first executable match winning) and rejects whatever `realpath` lands in agent-writable space or outside the configured roots. Stripping the directory to match the allowlist is what let `./ls`, `/tmp/x/ls`, `bin/nono why`, and `timeout 5 ./ls` run unprompted until 2026-07-27, so keep `resolveCommandName` and `unwrapCommand` returning paths intact.
- NEVER: resolve a command whose statement assigns `PATH`, `IFS`, `BASH_ENV`, `ENV`, `SHELLOPTS`, `BASHOPTS`, `CDPATH`, `GLOBIGNORE`, `PROMPT_COMMAND`, or any `DYLD_*`/`LD_*` variable — gate it instead, because the assignment redirects lookup or injects code into the very binary the trust check vouched for (`PATH=/tmp/evil ls` and `DYLD_INSERT_LIBRARIES=x.dylib ls` both passed before that rule existed). Widen the set in `isExecInfluencingVar` rather than at individual call sites.
- ALWAYS: keep the two PATHs in play distinct, because conflating them is how a gate ends up reasoning about a lookup that never happens:
  - The PATH handed to bash is ours: build it from `binTrust` via `resolveTrustEnv` and pin it in `wrapBashCommand`, rather than inheriting pi's ambient PATH or checking one against the other — a login PATH is nobody's groomed artifact and can carry entries bash resolves against the agent's own directory, as `/etc/paths.d` does here with an unexpanded `~/.dotnet/tools`.
  - The PATH a command resolves under stays the agent's: `PATH=./node_modules/.bin npm test` is legitimate work, so gate the statement for review instead of rewriting the command, exporting a read-only PATH, or stripping the assignment.
- NEVER: read gatekeeper's own config from the session `cwd`; instead take it only from `~/.pi/agent/extensions/gatekeeper.json` (`gatekeeperConfigPath` in `src/config.ts`), because the `pi-tools` profile grants the agent write access to its working directory, so a project-local `.pi/gatekeeper.json` let it award itself `danger` mode or a rubber-stamp `auditor` on the next session (removed 2026-07-27).
- ALWAYS: widen bin trust through that file's `binTrust` rather than in code, and prove the result with `mise run test`:
  ```jsonc
  // One list, two jobs: bash's search path AND the trust set. Order is
  // miseTools (via `mise which`, dir kept) then roots — the `,sb` shape.
  { "binTrust": { "miseTools": ["nono", "rg"], "roots": ["~/bin", "/usr/bin", "/bin"] } }
  ```
  Since this list is also the PATH, it must carry what approved commands need — `gh`, `node`, `python`, `uv` — or they die with command-not-found after the user allows them. An entry therefore grants a location rather than a free action: which *names* skip the prompt stays `src/hazmat/allowlist.ts`'s call alone, so `gh pr create` and `node -e '…'` keep facing review, and `nono why` is the one mise tool exempt.

## Boundaries

- ALWAYS: treat `test/`, `mise.toml`, `AGENTS.md`, and `CLAUDE.md` as dev-only — `.chezmoiignore` keeps them out of the deployed target, where `node_modules` arrives via the repo's `run_onchange` deps script instead.
